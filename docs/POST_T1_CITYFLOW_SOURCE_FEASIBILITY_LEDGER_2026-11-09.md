## 1. Driver identity — generated engine IDs SOURCE-SUPPORTED; exact original-ID mapping UNRESOLVED

- [Standard flow loader, `engine.cpp` 106–150](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L106-L150) enumerates input flows `flow_i`, with no original driver-ID field in the inspected schema. [`flow.cpp` 6–20](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/flow/flow.cpp#L6-L20) creates `flow_i_0`, `flow_i_1`, ... on generation.
- [`flow.h` 16–34](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/flow/flow.h#L16-L34) declares one common vehicle template, per-flow interval, integer start/end, counter and `nowTime=interval`. With a one-time flow (`startTime=endTime`) and valid timing, a **one-vehicle-per-flow crosswalk** is plausible, not yet demonstrated for the archived original data.
- **Paper crosswalk (not implemented):** freeze input flow order by an immutable original-ID manifest; map `original vehXXXX ↔ flow_<index>_0`; preserve `p_i`, B*/C* requested times, eligibility, full original route and original ID outside the engine; require 1,000 exact distinct generated/finished IDs with no missing, repeated or extra vehicles. An arbitrary input reorder changes generated names and invalidates a naive ID pairing.
- [Manual injection Python binding](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/cityflow.cpp#L12-L39) exposes `push_vehicle`, but [C++ `Engine::pushVehicle`](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L693-L716) creates IDs `manually_pushed_<counter>`, **also not the original IDs**. Treat it as an alternate prospective path requiring a different crosswalk, not an implemented solution.
- **Unresolved:** static proof each one-time flow is valid and creates exactly one ID, full original-ID/eligibility preservation, deterministic order across B*/C*, engine error/abort behavior and route-invalid flow omission.

## 2. Exact original fractional departure schedules — **BLOCKED in standard flow-file loader**; alternate injection pathway UNRESOLVED

- [Official flow format](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/docs/source/flow.rst#L1-L30) defines inclusive `startTime/endTime`, `interval` and route. However, [the source loader explicitly reads `startTime` and `endTime` as `int`](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L147-L150). [`flow.h` 21–33](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/flow/flow.h#L21-L33) stores integers. The standard file pathway therefore cannot encode original 22.6s, 38.2s, etc. **No rounding is permitted.**
- [Official SUMO converter, `converter_v2.py` 716–729](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/tools/converter/converter_v2.py#L716-L729) explicitly uses `int(float(obj.attrib['depart']))` for both start/end. Its output is **lossy** for fractional T1 times; it is not an approved adapter.
- [`flow.cpp` 6–21](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/flow/flow.cpp#L6-L21) compares its current time to integer starts, then generates vehicles; actual entry may occur later when capacity is unavailable.
- **Important alternate candidate:** [Python `push_vehicle`](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/cityflow.cpp#L12-L39), [generated manual IDs](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L693-L716), and [floating engine `interval`](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L47-L54) suggest that manually injecting at matching simulation ticks **might** represent certain fractional times. The [official documentation](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/docs/source/start.rst) describes configurable step durations; [engine warning bounds](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L167-L175) recommend 0.2–1.5s steps.
- This is **not qualified**: no read-only audit yet establishes the exact lattice for all 1,000 source departures, injection-before/after-step semantics, substep floor/float precision, queue-entry time, replay clock or preservation of matched dynamics. No adapter or external injection controller is authorized in the current phase.
- Distinguish original preferred `p_i`, requested `s_i`, engine creation time and **actual road admission**. Treat loader truncation as a material **standard-path blocker**, not evidence all conceivable CityFlow interfaces are impossible.


## 3. Exact original fixed ordered routes — road/link primitives SOURCE-SUPPORTED; **full route equivalence UNRESOLVED**

- [Engine standard flow loader](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L118-L133) parses road IDs into a Route, but [official flow documentation](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/docs/source/flow.rst#L17-L25) defines them as source, destination and optional anchor roads; a source-provided list is not a promise of literal, immutable physical traversal.
- **Precise Dijkstra semantics:** [Router::updateShortestPath](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/router.cpp#L212-L244) starts at first supplied anchor and invokes [Router::dijkstra](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/router.cpp#L158-L211) between *each consecutive pair of anchors*, appending the chosen segment. Its relaxation costs depend on length or duration (depending on RouterType). If every original external edge is listed in order, **direct adjacency may yield the desired one-hop segment**. However, the algorithm can choose a different intermediate connection when an alternative path has lower weight or tie/order effects; or fail if a required connection is missing. Route substitution is **possible, not inevitable**.
- [Router's laneLink selection](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/router.cpp#L24-L75) requires permitted lane-level transitions; [Engine::planRoute](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L450-L475) initiates the path expansion before planned insertion. A source list with adjacent SUMO edges is not sufficient if the converted roadnet lacks the same laneLinks.
- The original **1,000** archived routes have **7,393 consecutive transition occurrences and 1,196 distinct ordered edge pairs**, all connection-legal in the original SUMO network. This verifies the **reference**, **not** CityFlow's topology or its Dijkstra outputs.
- **Static proof obligation, not implemented:** build an exact original external-edge → CityFlow directed Road ID crosswalk; for all 1,196 distinct transitions show legal roadLink/laneLink and check Dijkstra's selected segment is exactly the direct expected next Road, with no inserted or omitted external roads, including equal-cost tie cases. Then require 1,000 projected full routes identical to original lists and an explicit prohibition on subsequent route reassignment. If any path cannot be retained, record the exact ID and transition as a blocker rather than silently editing it.

**Current classification:** SOURCE-SUPPORTED road/anchor and lane-link APIs, **UNRESOLVED** exact T1 fixed-route preservation; no proof of inevitable rerouting.


## 4. Meaningful junction constraints — structural capabilities SOURCE-SUPPORTED; equivalence UNRESOLVED

- [Official roadnet schema](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/docs/source/roadnet.rst#L5-L80) provides directed roads, lanes, roadLinks, laneLinks and signal phases.
- [Vehicle intersection speed decision](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/vehicle.cpp#L337-L371) checks laneLink availability, downstream lane entry and intersection-cross conflict yielding; [engine cross notifications](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L317-L365) update vehicle interactions; [waiting-buffer admission](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L502-L514) models finite admission.
- These are **actual junction mechanisms**, but no per-junction static mapping has been shown between the original SUMO network's microscopic priority/turn conflict rules and CityFlow defaults or converted signals. The included converter is an example, not verified scientifically equivalent geometry/priority.
- **Required gap register:** every original external edge, priority junction, internal connection and lane turn → CityFlow road/roadLink/laneLink; signals; conflicting movements; yield priority; storage, spillback and queue treatment; unrepresentable cases. No geometry-only grid substitute.


## 5. Complete per-ID original-preferred-to-arrival cost — **aggregate-only pathway insufficient; noninvasive stepwise alternative UNRESOLVED**

### Source observations and possible noninvasive method (NOT EXECUTED)

1. [Flow::nextStep](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/flow/flow.cpp#L6-L21) registers an engine-generated ID and plan-route vehicle when a flow's requested time is reached; [Vehicle constructor](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/vehicle.cpp#L38-L46) records enterTime at *generation*, **not proven equal to actual admission**. [Engine::handleWaiting](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L502-L514) moves a waiting vehicle to a lane when available.
2. The [Python bindings](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/cityflow.cpp#L12-L40) expose **get_vehicles(include_waiting=True)**, **get_vehicles(include_waiting=False)**, **get_vehicle_info(id)**, **get_current_time()**, **next_step()** and aggregate **get_average_travel_time()**. [Engine::getRunningVehicles](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L780-L793) differentiates real vehicles from lane-changing shadow objects; [Engine::getVehicles](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L619-L627) can include waiting ones when requested. An external observation record could, in principle, track the first appearance in the waiting-inclusive set, first running appearance and a later disappearance from the inclusive set for each known original-ID crosswalk.
3. [Engine::threadUpdateLocation](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L281-L308) removes completed vehicles from vehicleMap and vehiclePool, increments finishedVehicleCnt, then deletes the per-vehicle object. The completion aggregation samples **getCurrentTime() before the end-of-step increment**; [Engine::nextStep](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L566-L594) performs location updates and possible removal, then increments step; [getCurrentTime](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L677-L681) returns step×interval. Therefore if disappearance is noticed **after** next_step returns, assigning that *returned* clock to arrival would be **one full step later** than the native finish accounting timestamp. The candidate would have to distinguish the **pre-step clock t** from **post-step t+Δ**, and determine if the physical completion event should be labeled t, t+Δ or bounded within that interval. The source does **not** qualify exact true destination-crossing time by itself.
4. [getAverageTravelTime](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L682-L692) combines cumulative finished-vehicle intervals and elapsed times for vehicles still in the pool. It cannot replace **1,000 per-ID a_i−p_i** and may include unfinished vehicles. [Replay update](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L518-L541) writes running positions, **not a guaranteed per-ID terminal event ledger**. A mere disappearance may also need to be distinguished from invalid flows, reset, error handling or shadow lifecycle.

**Prospective read-only source verdict:** the engine **does expose sufficient pieces to propose an observational transition ledger** without immediate internal engine changes. But exact completed-arrival reconstruction is **UNRESOLVED**, *not categorically BLOCKED by the simulator*: per-step pre/post snapshots, original-ID mapping, creation and waiting/running state, actual admission, finish/abort semantics, clock boundary and completeness must all be resolved before relying on it. No polling tool, replay, adapter or engine execution was implemented.

**Paper 1,000-row reconciliation (not implemented):** original_id, engine_id, eligibility, original preferred p_i, requested s_i, engine creation tick, actual first-running/admission tick d_i, completion transition bracket [t,t+Δ], selected and source-justified arrival a_i, complete/invalid/aborted status, route hash and behavioral control attributes. Require every original ID present exactly once, all truly completed, with **(s_i−p_i)+(d_i−s_i)+(a_i−d_i)=a_i−p_i** and total Σ(a_i−p_i). In-network queues are already reflected and never added twice.



## Matched per-driver behavioral and stochastic-control obligations

- **Identities are not enough.** The source-fixed original B*/C* controls hold the same printed original-B speedFactor and vType by ID across both arms, but CityFlow's [vehicleTemplate fields](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/engine/engine.cpp#L135-L149) describe physical speed/acceleration/headway/length, **not a proven semantic replacement for SUMO's speedFactor**. Declare a prospective, justified CityFlow attribute vector per original ID and keep it identical within CityFlow B*/C*; disclose loss of original SUMO behavioral heterogeneity if no faithful mapping exists. Do not reinterpret a different physics model as matching numerical SUMO travel times.
- [Flow::nextStep](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/flow/flow.cpp#L10-L18) consumes engine RNG when assigning vehicle priority and thread allocation; [Vehicle construction](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/vehicle.cpp#L38-L46) also uses the engine RNG; [Router::selectLaneIndex](https://github.com/cityflow-project/CityFlow/blob/81ee0f47659ca66177a71f81676691c58ee89184/src/vehicle/router.cpp#L94-L115) consumes RNG when selecting the first lane. Different B*/C* release order can reallocate random choices among engine-generated IDs. **Identical seed ≠ matched per-driver exogenous draws.**
- Required future control specification: immutable original-ID→engine-ID crosswalk fixed by a common source order, fixed input attribute vector and route per original ID, controlled initiation and thread count, a documented inventory of randomized initial priority/lane/driver attributes versus endogenous traffic-response randomness, and a source-supported pairing method or explicit residual confound statement. Never silently turn off random behavior, relax the vehicle model or modify engine source during this phase.
- CityFlow's flow loader, manual push API and dynamic route setter are different pathways with different IDs and clocks. Source findings about one do **not** qualify another; a new protocol must choose and freeze one before any later implementation or execution.
